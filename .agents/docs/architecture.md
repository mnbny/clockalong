# Architecture

- Tauri 2 desktop app with a Rust backend in `src-tauri/`.
- React 19 + TypeScript + Vite frontend in `src/`.
- Frontend UI stack: Tailwind CSS 4, daisyUI, Tabler Icons, Oxanium, and Sonner.
- Frontend entrypoint is `src/main.tsx`.
- Frontend routing uses TanStack Router with file-based routes in `src/routes/`.
- The app shell owns window layout and the titlebar. Shared theme state controls the app palette and native window appearance.
- TanStack generates `src/routeTree.gen.ts`; it is ignored and regenerated by `tsr generate`.
- Use TanStack `Link` directly with daisyUI/Tailwind classes. daisyUI provides classes, not React components.
- TanStack Query owns remote fetch execution.
- A shared Dexie database owns the IndexedDB schema for durable bulk caches. Clockify, Linear, GitHub, and Telegram notifications use Dexie for storage and reactive reads.
- Dexie's official React hook owns live-query subscriptions and result retention. Widget adapters add inline errors, retry, account scoping, and cancellation for paged scans.
- App shell and window behavior spans frontend layout/CSS plus Tauri window config and capabilities.
- Reusable frontend components live in `src/components/`; shared frontend helpers live in `src/utils/`.
- Frontend-to-Rust bridge calls live in clients under `src/services/tauri/`; route code should use those clients instead of raw `invoke`.
- External frontend API clients live under `src/services/<provider>/`; Clockify uses a generated Zodios client under `src/services/clockify/`.
- The frontend MCP boundary normalizes snapshots, controls timers, creates completed entries, lists Telegram destinations, and sends Telegram messages through existing provider services.
- Work sources can be external providers such as Linear and GitHub or local sources such as Quick Timers. Do not force a generic provider abstraction until multiple implemented sources prove the common shape.
- Import directly from source modules instead of internal re-export files.
- Keep simple logic near its use. Extract helpers when reuse or a separate responsibility justifies them. These rules apply to TypeScript and Rust.
- Shared frontend constants group build-mode detection and local development flags. Development-only behavior must also check the build mode.
- Keep comments that explain constraints or behavior the code does not show.
- Let TypeScript infer obvious return types. Preserve explicit boundary contracts and Rust's required signatures.
- Use boolean expressions when a JSX condition otherwise renders nothing. Keep ternaries when both branches render content.
- Native auth is split by responsibility:
  - `src-tauri/src/auth.rs`: Tauri command surface, public auth snapshot, and auth-state events.
  - `src-tauri/src/auth_clockify.rs`: Clockify API-key validation and secure credential lifecycle.
  - `src-tauri/src/auth_linear.rs`: Linear OAuth, loopback callback, token refresh, and disconnect.
  - `src-tauri/src/auth_github.rs`: GitHub PAT validation, secure credential lifecycle, and disconnect.
  - `src-tauri/src/stronghold.rs`: narrow Stronghold read/write/remove helpers for native secrets.
- Native MCP modules split responsibilities:
  - `src-tauri/src/mcp.rs`: reads stored enablement, reports server status, and owns the Tauri commands.
  - `src-tauri/src/mcp_http.rs`: owns the loopback listener and validates HTTP requests.
  - The protocol layer negotiates MCP, defines public tool schemas, validates arguments, and answers cached tracking reads.
  - The bridge owns the cached snapshot, pending webview commands, request deadlines, and single-use attachment access.
- Auth routing uses Clockify as the app-level gate:
  - `/` waits for native app initialization, then navigates to `/dashboard`.
  - `_app` guards authenticated routes and redirects users to `/sign-in` only when Clockify is unauthenticated.
  - `_auth` only waits for app initialization; it does not redirect authenticated users away from the sign-in screen.
  - The sign-in screen lets users connect Clockify plus optional providers, then explicitly navigate with `Go to dashboard`.
  - Optional provider surfaces gate themselves. Linear and GitHub UI should render only when the matching provider is authenticated, while Clockify-only and local sources can remain available.
  - Rust exposes authentication state through `clockalong_auth_get_state` and `clockalong-auth:state-changed`.
- Tauri configuration lives in `src-tauri/tauri.conf.json`.
- Tauri permissions live in `src-tauri/capabilities/`.
- Repo-local agent skills live in `.agents/skills/`.

- Logging follows the shared Rust/frontend diagnostics pattern documented in `logging.md`.

Telegram uses a private frontend service for MTProto authentication, selected-group operations, and SDK realtime updates. Rust stores the session and group reference and publishes authentication state. One provider owns the client above routes and depends on TanStack Query. The sign-in screen and Settings use the same interactive QR/password dialog.

Telegram conversation records live in memory in TanStack Query. Each account and group connection has a separate cache scope. Provider services exclude unrelated account data from the cache. Query owns scoped history, topics, and group metadata. A bounded native disk cache retains only avatar and preview bytes across restarts. Service methods retain message projection and bounded avatar and preview reads. The notification collector uses group-wide history and scoped realtime events independently of the conversation cache.

MCP sends call the scoped Telegram service directly. Request deadlines and account/group teardown control cancellation. The service reconciles confirmed records into existing read caches and retains only in-flight message IDs for deletion safety. It does not retain attachment inputs or failed sends for UI retry.

Telegram's service lifetime belongs to the app-wide provider, independent of routing and Clockify authentication. The sign-in screen and Settings provide account setup. Settings also provides group selection. The provider also owns persistent notification collection. The root layout shows the floating notification feed across routes. Dexie owns card content and visibility; Telegram read status does not control local clearing. No chat component, draft state, or read acknowledgement observer mounts.

## Frontend providers

Frontend providers are composed in `src/main.tsx` through `ProviderRegistry`. Keep provider order explicit when one provider depends on another.

The theme provider receives the saved theme before the app renders. It keeps the header and Settings selections consistent and applies changes to the app palette and native appearance.

`ClockifySyncProvider` depends on TanStack Query and therefore mounts inside `QueryClientProvider`. It owns background sync into the local Clockify database. Routes and widgets query the database instead of starting broad Clockify entry pagination.

Work-source sync providers also mount inside `QueryClientProvider`. `LinearSyncProvider` owns the background sync into the local Linear ticket database. `GithubSyncProvider` owns the background sync into the local GitHub database. Routes consume those local records instead of starting broad provider pagination.

The app header and MCP use one shared full sync action for tracking data. It syncs enabled work sources and refreshes Clockify entries, the running timer, and summaries. Concurrent callers share the work. Failed or paused requests produce an explicit sync error. Telegram discovery and sends use separate scoped commands.

Provider widgets do not expose refresh controls. Only the app header refresh icon shows global sync activity.

## Frontend surfaces

Dashboard routes should stay thin composition shells. `src/routes/_app.dashboard.tsx` renders provider/source widgets and should not own provider fetches, sync state, table logic, or quick timer state.

Current dashboard widget boundaries:

- `src/components/ClockifyWidget.tsx`: Clockify summary, running timer, overlap repair, optional dashboard project override, and Clockify-centric dashboard controls.
- `src/components/QuickTimersWidget.tsx`: Quick Timer visibility, active preset lookup, preset CRUD, and preset start forms. It returns `null` when Quick Timers are disabled.
- `src/components/GitHubWidget.tsx`: GitHub auth gate, synced work-item live query, Clockify summary merge, issue and pull request table, and GitHub timer controls. It returns `null` when GitHub is unauthenticated.
- `src/components/LinearWidget.tsx`: Linear auth gate, assigned-ticket live query, Clockify summary merge, Linear ticket table, ticket ordering, and Linear timer start/stop controls. It returns `null` when Linear is unauthenticated.

Dashboard widget shells use `card card-border bg-base-200/10 dark:bg-base-200/40`. Use a `card-body` with `p-0` when the widget manages its own header, tables, or row dividers.

The settings route owns the page header and composes sections in this order:

1. Quick Timers
2. Clockify
3. Linear
4. GitHub
5. Telegram
6. App

Shared settings row/section layout lives in `src/components/settings/SettingsSection.tsx`. Keep section-specific hooks and service calls inside the scoped settings component that renders that section.

Settings groups use the same card treatment through `SettingsSection`; do not wrap individual rows in extra cards.

Settings reuse the existing control styles. Disconnect and Unlink use danger buttons. Connection states use success or error badges. Inputs use the primary style. Action icons and loading indicators match the other settings controls.

The Clockify description template for Linear issues is rendered from `src/components/LinearSettings.tsx`, not Clockify settings, because the template variables are Linear-specific even though the created entry belongs to Clockify.

## Frontend query keys

TanStack Query cache keys live in `src/lib/query-client.ts` next to the shared `QueryClient`. Add new app-level keys to the exported `queryKeys` namespace instead of defining arrays in routes, components, hooks, or provider service modules.

Use `QueryKeySegments<T>` when a key needs inputs:

- `params` is for request parameters, usually a small object whose fields mirror the query function options.
- `other` is for cache identity values that are not API params, such as local registries or objects used to derive merged client state.

For reads, import `queryKeys` and pass the returned key directly to `useQuery`. For invalidation or broad refetch, use the namespace root helper without input segments, for example `queryKeys.clockify.entrySync()` or `queryKeys.clockify.summaryReport()`, so all segmented variants under that prefix are matched. For full provider-session resets, use an explicit provider root such as `queryKeys.clockify.all`.

Provider service files should export fetch functions and DTO types, not query key constants. Cache identity belongs in one place; service modules stay focused on API behavior.

## Commands

- `pnpm dev`: run the Vite dev server.
- `pnpm run worktree:run`: launch Tauri with the worktree port and forward extra arguments to `tauri dev`.
- `scripts/worktree-setup.sh` or `pnpm run worktree:setup`: install asdf tools and dependencies, copy missing local env files from the primary Git worktree, and prebuild the Rust backend.
- `pnpm build`: run `tsr generate && tsc && vite build`.
- `pnpm preview`: run the Vite preview server.
- `pnpm release:mac`: run the local Apple Silicon release build, updater signing, DMG notarization, stapling, and verification flow.
- `pnpm release:github`: build locally and create or update a draft GitHub Release through `gh`.
- `pnpm tauri`: run the Tauri CLI.

Validation runs formatting, linting, and TypeScript checks in a defined order. Scripty discovers validation steps from the package manifest and stops when a step fails.

The project pins Node.js, pnpm, and Rust versions for development.

JavaScript and TypeScript tests use Vitest with a separate configuration that excludes frontend build plugins. Tests are grouped by feature in one directory. Type checking covers tests and application code. Rust tests use Cargo and can stay beside private modules. Test execution is separate from validation. Repository agent instructions define when to run tests and which behavior needs regression protection.

Worktree scripts follow the Toolkit TypeScript/zx pattern and are independent of the harness. The shell setup entrypoint installs dependencies before loading TypeScript, so it also works in a fresh checkout. `scripts/worktree-utils.ts` owns logging, Git worktree discovery, local-file copying, and port validation. Setup copies missing base, development, and production environment files from the primary worktree and preserves existing local files. Run selects the first nonempty port from `WORKTREE_PORT`, `PASEO_PORT`, `CONDUCTOR_PORT`, `PASEO_WORKTREE_PORT`, and `PORT`, then falls back to `1420`. `conductor.json` and `paseo.json` call these same entrypoints.

The development launcher uses Vite's standard environment-file precedence. It forwards only app-prefixed values from those files to the native child, while preserving the inherited process environment. Exported values take precedence. The normal Run action uses this launcher; direct Tauri invocation bypasses it.

Worktree setup copies local configuration from the primary checkout. It does not copy changes back. Configuration kept only in a disposable worktree can be lost when that worktree is removed.

The release launcher uses Vite production precedence and forwards app, Apple, and updater-signing configuration to the existing shell scripts. Exported values take precedence. Release commands preserve arguments, stdin, and exit codes without loading development environment files.
